It rejects duplicate event IDs, identifies missing sequences, blocks conflicting instructions, prevents unsafe simultaneous processing claims, preserves evidence, and provides read-only safety diagnostics.

**The last test run reported 87 passing receiver tests.** These are meaningful protections, but they do **not** mean FundX can place orders. ## 5. Completed receiver functionality — what and why

The following reflects the methods and behaviors discussed and tested. **Inspect the actual file before making edits; the assistant has not freshly loaded the entire current source.**

### 5.1 Durable SQLite tables

The receiver's schema includes at least:

| Table | Known purpose |
|---|---|
| `received_events` | Tracks accepted event IDs to prevent duplicate consumption. |
| `message_sequences` | Tracks sequence progress per session. |
| `sequence_gaps` | Persists unresolved missing sequences. **Actual known columns:** `session_id TEXT PRIMARY KEY`, `missing_sequence_number INTEGER NOT NULL`. |
| `instruction_inbox` | Stores `event_id`, `session_id`, `sequence_number`, original `payload_json`, and `processing_status`. Known statuses: `RECEIVED`, `PROCESSING`; unique `(session_id, sequence_number)`. |
| `message_integrity_halts` | Stores one global durable conflicting-duplicate halt, including reason, event ID, original payload, and conflicting payload. `halt_id INTEGER PRIMARY KEY CHECK (halt_id = 1)`. |

The code uses SQLite transactions and `BEGIN IMMEDIATE` for critical acceptance/claim operations, serializing competing writers to the same database.

### 5.2 Validation and atomic acceptance

`accept_instruction(event_id, session_id, sequence_number, payload_json)` validates event/session IDs, sequence numbers, and a non-empty JSON object. It verifies that the JSON's identifiers match the method arguments. The event ID, sequence progression, and full payload are intended to commit together.

Why: The receiver must not treat malformed or mismatched metadata as valid trading instructions. It must not consume an event ID without preserving the corresponding accepted instruction, and must not advance the sequence improperly.

### 5.3 Event deduplication and sequence gaps

- Reusing an accepted `event_id` does not create a second instruction.
- A missing sequence number is recorded durably; an unresolved gap blocks new instruction acceptance and processing.
- A rejected gap-causing event ID is not permanently consumed, so a controlled recovery path can later revisit it.
- `has_sequence_gap(session_id)` reports session-specific gaps; `_global_gap_exists()` checks across sessions.
- `clear_sequence_gap(...)` was intentionally left without a permissive automatic clearance path; do not casually implement a bypass. Design recovery around authenticated retrieval, replay, verification, and reconciliation.

Why: Missing or out-of-order instructions can radically change intended positions. FundX must fail closed rather than guess.

### 5.4 Durable inbox and processing claim

- `list_pending_instructions()` returns `RECEIVED` items in stable sequence order.
- `mark_instruction_processing(event_id)` atomically claims a pending item as `PROCESSING` only if global safety checks allow it.
- `list_processing_instructions()` reports claimed work.
- `has_interrupted_processing()` detects any item left in `PROCESSING`.
- A global restriction prevents claiming new work while another instruction remains in `PROCESSING` and requires reconciliation.

Why: A crash between receiving an instruction and completing its downstream work must not cause blind replay or double execution. **At this stage `PROCESSING` is only an internal receiver state; it does not prove an exchange order was sent.**

### 5.5 Conflicting duplicate detection and durable global halt

A **conflicting duplicate** is a repeated event ID with a different raw JSON payload. The method `is_conflicting_duplicate(event_id, payload_json)` performs a read-only comparison.

The duplicate branch in `accept_instruction()` now:

1. Checks the original stored `payload_json` if the event ID already exists.
2. Rejects an identical duplicate normally.
3. For a different payload, writes a durable global record to `message_integrity_halts` with the first conflict evidence, then commits the halt without overwriting the original inbox instruction.
4. Rejects the conflicting message.

The single-row halt record is deliberately **first-wins**; later conflicts cannot overwrite the initial evidence. There is no automatic clearance method.

Why: An event ID that identifies two different trading instructions is a serious message-integrity failure. Simply ignoring the second message could hide a strategy or transport defect. The system must stop and preserve evidence.

**Nuance:** Raw-text comparison treats semantically equivalent JSON with different whitespace or key ordering as different. This was the implemented strict behavior; revisit canonicalization only through a deliberate protocol decision and tests, never silently.

### 5.6 Global halt enforcement

Both `accept_instruction()` and `mark_instruction_processing()` check `has_message_integrity_halt()` **inside their `BEGIN IMMEDIATE` transactions** and reject work while halted.

Why: It is insufficient to halt only order processing while continuing to ingest potentially unsafe new instructions. Multiple receiver instances sharing the same SQLite file must see and honor the same durable halt.

### 5.7 Read-only operator diagnostics

Known methods:

- `has_message_integrity_halt() -> bool`
- `get_message_integrity_halt() -> dict | None` — returns `reason`, `event_id`, `original_payload`, `conflicting_payload`.
- `get_message_integrity_halt_report() -> str | None` — human-readable report including halt status, blocked acceptance/processing, event ID, both payloads, and investigation guidance.
- `get_receiver_safety_status() -> dict` — aggregates three receiver-level blockers.

Known status structure:

```python
{
    "safe_to_process": False,   # False if any of the three blockers is active
    "message_integrity_halt": True,
    "sequence_gap": True,
    "interrupted_processing": True,
    "reasons": [
        "MESSAGE_INTEGRITY_HALT",
        "SEQUENCE_GAP",
        "INTERRUPTED_PROCESSING",
    ],
}
```

**Critical interpretation:** `safe_to_process=True` only means these **three receiver checks** are clear. It is **not** a global trading-readiness signal and must never be used alone to authorize Coinbase order submission.

## 10. Safety invariants to preserve during future changes

1. **No order leaves IPC without IPC risk approval.**
2. **A received message is not an approved order; `PROCESSING` is not a broker execution.**
3. **Duplicate event IDs cannot create duplicate broker orders.**
4. **Conflicting duplicates trigger a persistent global halt and preserve the original evidence.**
5. **Unresolved sequence gaps block unsafe progress.**
6. **Interrupted/unknown work must be reconciled, not blindly retried.**
7. **All critical accept/claim/reserve/order transitions must be durable and race-safe.**
8. **Restarting never silently clears halts or assumes a flat broker account.**
9. **Unknown broker position, working orders, margin, or session state means no new order authority.**
10. **No accidental reversal on close/reduce-only orders or partial fills.**
11. **Reports carry Jack's order ID and clearly distinguish requested, approved, and filled quantities.**
12. **Production and staging are isolated; no shadow component can send real orders.**
13. **Diagnostics must not mutate safety state.**
14. **The current receiver `safe_to_process` flag must never be interpreted as production `safe_to_trade`.**
